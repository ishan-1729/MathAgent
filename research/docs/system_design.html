MathAgent — System Design

A training-free agentic harness that proves elementary number-theory theorems — and proves that the proofs are elementary.

The one-sentence version. Frontier LLMs (Codex / GPT-5.5-xHigh) are orchestrated inside a LEAP-style blueprint→DAG→compiler-feedback loop to find a number-theory proof; that proof is then formalized to Lean and put through a non-gameable proof-term dependency + axiom audit that certifies it is elementary — because a correct non-elementary proof is a failure, not a success.

This is the visual companion to system_design.md (the deep written version). For what is built/validated right now see build_status.md; for the staged plan, PLAN.md.

1.One system, one spine, grafts

The 20 systems papers in the corpus are a component menu, not competing blueprints. The spine is LEAP (informal blueprint → AND-OR proof DAG → compiler-feedback revision → memoized reuse). Onto it we graft mechanisms from others, substitute one piece we can't reproduce, and add the one thing no paper targets — the elementary gate.

2.The certification pipeline

The unit of work is a step-ledger (a proof as a typed DAG of justified steps). It flows through two clearly separated halves — ① find the proof, then ② certify it's elementary — and yields two distinct verdicts that must never be conflated:

  • PROVEN an informal proof was found and passed the soft + structural gate.
  • authoritative_elementary that proof was formalized, compiled against Mathlib, its proof term audited as elementary, and its Lean statement verified faithful to the claim.

3.The defining mechanism — the layered gate

The elementary constraint is enforced defense-in-depth, cheap-first, but only the last layer is authoritative. Two facts force this design: elementarity has no projection operator (you can't "round" a class-group argument into a descent argument — so it must be a verification gate, not a projection), and a judge is never the final gate (same-model judges inherit the prover's blind spots).

Lean-verified ≠ elementary. Mathlib is the heavy machinery; a compiling proof can route through class groups or Mihăilescu. So Layer 4 audits the kernel proof term's transitive dependency closure, not "it compiled."

Boundary rulings — the contested edge of "elementary"

Most justifications are simply allowed or not, but a handful sit on the genuine boundary, where a binary flag is wrong. allowed_toolkit.yaml carries a separate four-valued boundary_rulings vocabulary (queryable via Toolkit.ruling()): allowed (e.g. Pell's fundamental solution — an elementary descent proof exists), allowed_with_citation (e.g. Zsygmondy — elementary but hard, cite it like LTE), allowed_per_problem_whitelist (e.g. higher / cubic–quartic reciprocity — admit only where a specific problem needs it), and disallowed (e.g. the analytic / Gauss-sum proof of quadratic reciprocity — even though a different, elementary proof of the same theorem is fine). It is the explicit, auditable answer to "what counts as elementary at the edge" — though it is declared, not yet gate-wired (Toolkit.ruling() exists, but no layer consults it yet; enforcement is a tracked follow-up). The gate also fails closed: any malformed ledger or internal exception becomes a REJECT, and the verdict is the maximum severity present (REJECT > REVIEW > INFO), so a bug can only ever produce a safe rejection, never a silent pass.

The faithfulness wall — proving the right theorem

A Lean proof can pass the kernel and the elementarity audit yet prove a subtly different statement — a weaker special case, or a vacuously-true one with impossible hypotheses (AlphaProof_Nexus "solved" wrong density variants this way; Goedel: >80% of failures are misformalization). So after compile+audit an adversarial panel (faithfulness.py) checks the Lean statement against the English claim through four diverse lenses — back-translation, quantifiers/domain, vacuity, strength — each told to actively find a discrepancy and default to "unfaithful" if unsure. The statement is accepted only if at most max_unfaithful lenses object (default 0 — unanimity). Diverse lenses, not N identical judges, each catch a different failure mode — so authoritative_elementary also means faithful. It fails closed: if no faithfulness panel ran, the result is not authoritative (the CLI defaults the panel on for certification; --no-faithfulness is explicitly audited-only). Authoritative also requires the informal gate to have passed deterministically, not merely NEEDS_REVIEW.

4.How mechanisms engage — there is no classifier

A natural question: what decides whether decomposition, population search, or the tournament runs? Nothing learned. It is a deterministic control-flow cascade + config flags (DagDriver._prove):

  • Ralph loop (direct attempt) — unconditional; every node tries this first.
  • LEAP decomposition — only if the direct attempt failed (the cascade falls through).
  • Population / Elo + PUCT + Bradley-Terry — if population_k and comparator (the --population flag); lives inside decomposition.
  • Autoreason tournament — if refiner is not None (the --refine flag); refines a directly-proven ledger, monotonically (never regresses).
  • Re-plan — bounded by max_replan_depth; deep-hash cache — always on (inert when there's nothing to reuse).

So "the easy theorem didn't use the DAG" means only that the direct attempt succeeded and the cascade short-circuited. The only intelligence in the gating is try-cheap-first, escalate-on-failure — which is LEAP's design, not a classifier.

5.Where it breaks — two orthogonal axes

Proof difficulty and formalization difficulty are nearly orthogonal, and the system is lopsidedly tooled across them. All the rich machinery targets finding the proof; the formalization step has essentially one tool — prompt → compile → local-patch repair. Once search is cheap, the bottleneck moves to the under-tooled axis.

6.Search machinery — Population / Elo / Bradley-Terry / PUCT, explained

These are search-efficiency tools — they never change whether a proof is accepted (that's the gate). They solve one concrete problem worth understanding from scratch.

The problem. When the driver decomposes a goal it can ask Codex for K candidate decompositions. We don't know which is best, and testing one (recursing in to prove it) is expensive; what's cheap is asking a judge to compare two. So: rank K items from noisy pairwise comparisons, then decide which to spend the next expensive attempt on. Three standard tools, one per sub-problem.

Elo — an online rating from pairwise results

From chess. Each candidate gets a scalar rating R. The chance A beats B is logistic in the rating gap, E_A = 1 / (1 + 10^((R_B − R_A)/400)); after a result S_A ∈ {1, ½, 0} nudge toward the surprise: R_A ← R_A + K·(S_A − E_A). That's online gradient ascent on a logistic model — cheap, one update per comparison, but order-dependent.

Bradley-Terry — the same model, fit as a batch MLE

The model Elo approximates: each item has a latent strength s_i with P(i beats j) = s_i / (s_i + s_j) (a logistic in log s). From the full win matrix we compute the maximum-likelihood strengths directly via the MM iteration s_i ← w_i / Σ_j n_ij/(s_i + s_j) (then renormalize). It uses all the data at once → order-independent and more stable than online Elo. So Elo updates during the tournament; Bradley-Terry re-fits from the whole matrix after.

PUCT — what to expand next (explore vs exploit)

Trying a candidate is expensive, so don't blindly pick the top-rated one — a barely-tried promising one deserves a shot (the multi-armed-bandit trade-off). PUCT (AlphaZero's MCTS rule) scores score(a) = Q(a) + c·P(a)·√(ln ΣN)/(1 + N(a)): exploit the strength Q(a) plus an optimism term that's large for under-visited candidates (N(a) small) and decays as you revisit — the UCB1 idea. Pick the argmax, expand, increment its visits, repeat.

The Autoreason tournament reuses the same two estimators for a different job — revision control. Each pass: Critic → Author → Synthesizer → blind judge panel; Bradley-Terry turns the votes into strengths and PUCT seeds the next pass. A challenger displaces the incumbent only if it beats it by a margin and passes the elementary gate; "do nothing" wins ties; stop after k=2 wins. So refinement is monotone — a "better-sounding but non-elementary" revision can never displace a correct elementary one.

7.The proof DAG — AND-OR structure & memoization

§4 keeps saying "DAG" and "decompose"; here is what that machine actually is, from scratch. Like §6, this is search structure — it changes how fast a proof is found, never whether it is accepted (that is the gate, §3).

AND-OR nodes — how a plan becomes a graph

Think of planning a hard proof: "I can prove T if I first prove these lemmas." An OR-node is a goal, dischargeable two ways — a direct proof, or one decomposition (OR = any one route suffices). An AND-node is a decomposition: a sketch that proves the parent assuming sub-lemmas, so all children must hold (AND = every part required). Children are themselves OR-nodes, so it recurses. The driver walks it depth-first, backtracking the instant a child fails (dag_driver.py::_prove) — §4's "try-cheap-first, escalate-on-failure" made concrete. Before a plan is trusted it must pass two soundness checks: honest-decomposition validation (the sketch's lemma-steps must exactly match the declared children — no hidden gap) and the LEAP reviewer (each child non-circular and strictly simpler; soft, never certifying elementarity — only Layer 4 does).

Memoization — prove each sub-lemma once

Memoization is the dynamic-programming trick of caching an expensive result so an identical sub-problem is solved once and reused. Proof search is full of overlapping sub-problems — the same lemma resurfaces on many branches — so every goal is a node keyed by its hash (get_or_create); a second occurrence is a cache hit that reuses the stored proof (marked shared), and failures are cached too (never re-attempted). This is what collapses an exponential re-derivation (LEAP's tree baseline re-proves the same lemmas over and over) into a tractable graph — and it is why the tree becomes a DAG (shared nodes reconverge).

Acyclicity — no circular proofs

A cache of "X is provable" is dangerous if a proof of X may assume X. Before committing a decomposition, would_create_cycle runs a reachability check and rejects any child that is the parent restated, an ancestor on the current path, or anything transitively depending back on it — keeping the graph acyclic, so "A because B, B because A" is impossible.

Why the hash is soundness-critical. The node key (goal_hash) folds only meaning-preserving surface differences (notation, synonyms, spacing) and never renames variables or reorders operands — a false hit (two distinct goals hashing equal) would reuse a proof of the wrong lemma. A miss only costs recomputation; a false hit would be unsound, so it biases hard toward never merging.

The Ralph loop — the always-on direct attempt

"Ralph" (AlphaProof_Nexus) turns one noisy LLM call into a self-correcting loop (ralph.py). Each episode: the prover emits a ledger → the deterministic gate re-checks it → on rejection its findings are appended as capped lessons-learned that condition the next episode, until the ledger is admitted or the budget runs out (then exhausted — never a false success). It is fixed-point iteration over proof attempts: the cheapest, always-on layer of §4's cascade, and the leaf behaviour at every DAG node's direct attempt.

9.Design invariants

  • The gate is the product — a correct non-elementary proof is a failure.
  • Only Layer 4 certifies "elementary." Layers 0–3 pressure/filter.
  • Never trust compile-success or hammer-success — always audit the proof term.
  • Judges rank; deterministic mechanisms accept.
  • The memo key never merges distinct goals (it folds notation/synonyms but never renames variables — that would be unsound).
  • Everything terminates (Budget caps → honest EXHAUSTED).
  • No teaching-to-the-test — improvements are problem-independent and measured on held-out problems.
